# CI/CD Pipeline Documentation

## Overview
This project uses **GitHub Actions** for its Continuous Integration and Continuous Deployment (CI/CD) pipeline, specifically tailored for building and distributing Android binaries (APK).

## Architectural Decisions

### 1. Build Infrastructure: GitHub Actions vs Expo Application Services (EAS)
By default, Expo projects heavily rely on Expo's cloud infrastructure (EAS Build) to compile native Android/iOS applications. However, we have chosen to bypass EAS and compile the application **entirely locally on GitHub Actions runners**.

**Why we chose this approach:**
- **Zero External Dependencies:** It completely removes the need for an Expo account, Expo authentication tokens (`EXPO_TOKEN`), and EAS quotas.
- **Cost-Effective for Low Frequency Deployments:** Since deployments are not expected to be highly frequent, utilizing the free computing minutes provided by GitHub Actions is more than sufficient.
- **Unified Ecosystem:** Everything from source code to artifacts and releases is managed strictly within GitHub.

**How it works:**
1. The GitHub Ubuntu runner sets up Node.js and Java (JDK 17).
2. `npx expo prebuild` is executed to generate the native Android project directory on the fly.
3. Gradle (`./gradlew assembleRelease`) is invoked directly to compile the APK natively.
4. The resulting APK is uploaded as a GitHub Artifact and optionally attached to a GitHub Release.

### 2. Deployment Trigger Strategy
- **Continuous Backup (Artifacts):** Any push to the `main` branch automatically builds the APK and uploads it as a temporary Artifact (retained for 30 days) attached to the workflow run.
- **Formal Releases:** Pushing a git tag matching `v*` (e.g., `v1.0.0`, `v0.2`) triggers the build process AND automatically publishes a formal **GitHub Release**. The APK is permanently attached to the release page, making it incredibly easy for users and testers to download.

## Troubleshooting & Alternatives

### Potential Issues
- **Build Times:** Because we are generating native code and running Gradle from scratch on GitHub's standard runners, build times may be slightly longer compared to EAS.
- **Keystore / Signing:** Currently, the app is built using the default debug/release keystore generated by Expo/React Native. If you plan to publish to the Google Play Store in the future, you will need to generate a production Keystore and configure it in the GitHub Actions environment secrets.

### Fallback Alternative (Expo EAS)
If the local build approach encounters issues (e.g., GitHub Actions runner limitations, complex native module errors, or if iOS builds are required in the future without macOS runners), the pipeline can be easily reverted to use Expo's Cloud (EAS):

1. Create an account on Expo (expo.dev) and generate an Access Token.
2. Add the token to GitHub repository secrets as `EXPO_TOKEN`.
3. Modify `.github/workflows/android-build.yml` to use `expo/expo-github-action@v8` and execute `eas build --platform android --profile preview --non-interactive` instead of running Gradle locally.
